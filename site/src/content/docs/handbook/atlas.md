Atlas reads a repository and writes a page that says how it works: what comes in, what runs, where it lands, who reads it, what breaks what, what changed since the last map, and where to start reading. No sentence on that page is written by a person. It is derived from the workflows, the manifests, the imports, the writes and reads in the code, the tools the workflows run, and the git history, and it is regenerated whenever the repository changes.

The page is for anyone who has to understand a repository they did not write: a new contributor, a reviewer, an operator, or a model.

This repository's own page is [`atlas/README.md`](https://github.com/dogfood-lab/testing-os/blob/main/atlas/README.md). The site renders every mapped public repository at [`/atlas/`](../../atlas/): the page, a flow picture of its busiest door, a bar picture of what breaks what (production importers as a solid bar, test-only importers continuing it dashed, the doors on the path as a numeral), a strip of the weekly renders since the first, and the one line a person may write, with a link that opens the boundary file on the repository's default branch. The specification the page is measured against is `docs/atlas-page.spec.md`, a page written by hand for this repository and approved before the generator existed. The engine was then run on a Python repository and a TypeScript repository it had never seen, and every sentence that misled a newcomer there was fixed at the class, with a test that fails against the previous engine.

## What a page says

| Section | Where it comes from |
|---------|---------------------|
| What this is | The count of parts and every language in them, with the data named first when images are most of the files ("mostly images (6651 files); code in JavaScript (2), TypeScript (2) and Python (1)"); the count of doors and the busiest one: the one that commits into the repository and reaches the most parts, else the one with the greatest reach, a tie stated and broken toward the door a pull request goes through; the page states the rule when it applies. Then what the repository publishes to, the commands people run, the desktop app people install (a Tauri crate's bin), the game Godot runs (`run/main_scene` in `project.godot`) and the package they import, read from its manifests; a package whose every exported file starts a program as it loads is "the package's entry, which runs the command X; it is not a library", and a private workspace member's bin is "a command bundled into" the package that names its built path. |
| What changed since the last map | The structure just derived compared with the one committed at HEAD: new imports between parts (a new edge on a dependency cycle first), doors added or changed, places gaining writers or readers, origin flips, steps gained or lost, parts added, removed or renamed, then file counts. |
| What comes in | Every workflow: what triggers it, what its steps run and what they only check (linters, type-checkers), read by the conventions of the tools they name (`npm run`, `pnpm` and `yarn` scripts with their workspace filters, `pytest`, `uv run`, `python -m`, `tsc --build`, `vitest`, `eslint`, `cargo` with its package selection, `cargo tauri`, `godot --script`, GUT and gdUnit4 runners, `gdlint` and `gdformat`, shell scripts, Makefile targets, spawned commands, including commands a helper hands to a shell with literal text, and a run of a build output such as `node dist/cli.js`, traced first to the entry a bundler's build names (esbuild, tsup, rollup, `vite build --ssr`) and then through the tsconfig the build names; `vite build` and `vite dev` run the app's config and its `src/`). Then every command a manifest installs (a `bin` in `package.json`, a `[project.scripts]` entry in `pyproject.toml`, a `[[bin]]` or `src/main.rs` in a `Cargo.toml` crate) and the entry of the package, said as published only when a door publishes it, each a door of its own. A container, wheel or binary build runs the file it starts (a Dockerfile's `ENTRYPOINT` or `CMD`, traced through stages, `WORKDIR` and `COPY`) and checks the files it packs. A child process that starts a module of this repository (`python -m <package>`, `node <file>`) connects the parts; `git` and `gh` are said as "runs git". A tracked file handed to a tool the map has no rule for is a checked run, a `cd` moves the rest of the step, and a job or step gated by an `if` on the event, the ref, its type or an input, or held off one (`!=`), keeps what it runs, deploys or commits to the events that remain ("deploys the site on a push to main"; "when run by hand with dry_run false, it also publishes"). A publish names what it sends: a package chosen by its directory or by the tag, the VS Code Marketplace or Open VSX for an extension, nothing for a dry run; a Godot export is said as "exports the game for Linux". A job that checks the repository out into its own `path:` is read from inside that directory. |
| What happens through the busiest door | The parts its executed files are in, the parts reached through imports in order, the order of work inside the entry functions, the places it writes (a written-out file name lands on that file, not its directory; a path built from the directory the command is run in, from the home directory, from a temporary directory, from a helper that returns one, from an environment variable or from an argument the caller passes is not a place here; a write into a file the repository does not track is counted, never placed; a write skipped in CI, or behind a flag every run passes, is not credited to the door; a write behind a main guard (`require.main === module`, `import.meta.main`, `process.argv[1]` compared, `__name__ == "__main__"`) is credited only to a door that runs the file or starts it as a child process, never to one that imports it; a write made only when the file is absent is a bootstrap, credited to no door and never a stamp; a write under the working directory that spells a tracked place is that place, said as "when run from the repository root, and committed"), what it commits and pushes (staging is not writing: a door writes what its reach writes and what its steps' own redirects write, and a staged place with no writer is "written by people"), here, to a branch for review, or into a clone of another repository, what it changes in other repositories through the GitHub API, and what it dispatches, publishes or deploys. What a door only checks reaches parts but writes nothing. |
| Who reads the results | The files and workflows that read those places: code that reads or imports them, the site build that renders them, and tests, counted after the code; readers found by scanning text are marked and never counted as structure; a configuration file (a `*.config.json`, a manifest, a `tauri.conf.json`, an `AppxManifest.xml`) that names a tracked path is a reader of it, marked "(from configuration)"; a Markdown link, a path mentioned in prose, and a packaging list are not readers. |
| The other doors | The same facts for each remaining door, workflows and installed commands, in prose. |
| What breaks what | Parts by production import fan-in, with test-only importers counted separately, and by how many doors pass through them; places whose readers a hand edit would reach (a file its writer only stamps is never one); a part called over HTTP by another, with the count of routes. |
| What tends to change together | The strongest source-file pairs from the history, with the relation between their parts stated; a file and its own test set aside and counted. |
| What no test touches | Code parts no test file imports, directly or through one hop, including tests that spawn scripts; data and site parts are never asked. A Rust file holding `#[test]` or `#[cfg(test)]` tests its own part, and a part tested only that way is "tested only by the unit tests in its own files"; a GDScript file extending `GutTest`, `GdUnitTestSuite` or GUT's `test.gd` is a test wherever it lives. A part that tests reach only by spawning its files is said as "touched by tests only through a spawn". A test that rewrites tracked files is a writer of them, listed under Generated as "(a test)". |
| Written but never read | Places no code, workflow or test reads, named by file. |
| Helpers that look duplicated | Candidates from names and call order; the same name across three or more parts reads as a shared contract. |
| Generated, never hand-edited | Places with a writer in code, or in a workflow's own shell or a staged path its steps name (a `git add` alone writes nothing), whose commits are not mostly people's; a tracked file its writer reads first is said to have a block written by it and stays mixed, unless the read is only compared with what is about to be written, or the write happens only when the file is absent ("written once by X when absent"); a committed output of a run from the repository root is listed with that qualification; an untracked output is not a place. |
| Hand-authored | Parts nothing in the repository writes to, with the count of run-time-path writes that may land there; and places a workflow commits: those nothing writes ("written by people") and those people commit to more than their writer ("written by X, and by people: 67 of its 68 commits in the window are theirs"). |
| Where to start | A chain of files that run, from the door a pull request goes through whenever the busiest door is not it (release, deploy and schedule triggers included), beginning at that door's entry point rather than the first helper it names, to the first reader of its output; when that door runs only tests, the chain follows an installed command from its entry instead and says so; an arrow is never a check; a barrel is passed through to what it re-exports and a file holding one constant is neither a start nor an end; every arrow is a recorded edge (a run, an import, a write, a read), every step names a file, files with no statements, manifests and data files are skipped, a test is passed over for the production file it imports, and the chain ends in code. When nothing can be followed it says so. |
| What this map cannot see | Unresolved imports, imports of paths outside the repository, declared dependencies that share a name with a local module, files the parser cannot read (named, up to three, then counted by part with the construct that stopped it), paths built at run time, writes to the directory the command is run in, the home directory, a temporary directory or a path the caller passes, writes to files the repository does not track, commands built at run time (with how many of them are in tests), text-scanned readers, test files a Linux shell's expansion of a package script's `**` glob leaves out of CI, links over HTTP, writes and reads to the player's data directory (`user://`), deploy files no workflow runs (an image a workflow builds and none pushes, a Hugging Face Space nobody uploads, a Docker MCP Catalog entry no workflow submits), and the confidence of the history statistics. |

## Adopt it in a repository

```bash
npx --yes @dogfood-lab/atlas init
npx --yes @dogfood-lab/atlas map
```

`init` proposes `atlas/boundaries.yaml`: the named parts of the repository and the globs that own them. Correct the names and globs if the proposal is wrong; the one line a person may add is `summary`. `map` writes `atlas/README.md`, `atlas/page.json`, `atlas/structure.json` and `atlas/statistics.json`. Commit the folder. `map --divergence <file>` also writes the divergence report; a caller mapping a copy it made itself passes `--name owner/repo` when the clone carries no origin and `--baseline <dir>` holding the last committed map when the copy has none; `init --force` rewrites a boundary file from a fresh proposal. `init` also keeps the map out of what ships: it adds `atlas/**` to an existing `.vscodeignore`, `atlas/` to an existing `.npmignore` when the manifest has no `files` list, and `atlas/` to `.prettierignore` (created if needed) when prettier is a dependency or a script runs it; it never adds a line twice and says what it added.

Then run the check in the test job:

```bash
npx --yes @dogfood-lab/atlas check
```

It fails when a part gains or loses a dependency, a file changes part, a new file belongs to no part, a named part matches nothing, or a file belongs to two parts. When it fails after a change you meant to make, run `atlas map` and commit the regenerated `atlas/` files with the change; never edit the page by hand, and never change the code to satisfy the map. A repository with no `atlas/` folder is a notice and exit 0, so adopting Atlas reddens nothing. The codes it prints are listed on the [error codes](../error-codes/#atlas-codes) page.

## Ask about one file

```bash
npx --yes @dogfood-lab/atlas explain packages/ingest/persist.js
```

`explain` says what one file is in the system, for a person about to edit it or an agent in a coding session: its part, the doors that run it or pass through its part, what it imports and what imports it, its own test, where it writes and who reads that, the order of work inside it, and what it changes with. `--json` gives the same facts as fields. It reads the committed map and never maps again, so it answers at once and names the commit it describes.

## See the delta on every pull request

```bash
npx --yes @dogfood-lab/atlas diff --base origin/main
```

`diff` compares the committed map at a base ref with a fresh map of the working tree and prints the "what changed" section as markdown or JSON, writing nothing. This repository's CI runs it on every pull request and posts the result as one comment, updated in place, so a reviewer sees "ingest now imports dogfood-swarm" or "nothing structural changed" before reading the diff. The step never fails the build; on a fork it prints to the job log and summary instead.

Public repositories under `dogfood-lab` and `mcp-tool-shop-org` that have committed an `atlas/` folder are rendered weekly onto the `atlas-render` branch and appear on the site. A private repository uses the workflow template shipped in the package, `templates/atlas-refresh.yml`, and nothing leaves it.

## Run it for a private fleet

For repositories that must not leave your machine, the same engine ships as a container with persistent memory, `ghcr.io/dogfood-lab/atlas`, whose default command is `atlas-fleet`. It maps the repositories you list in `fleet.yml`, by mounted path or clone URL, once at start and then on a schedule, keeps every render and its history on a volume, and serves the same fleet list and per-repository pages as this site on a port of your choosing. Nothing leaves it except git fetches of the repositories you listed. The same image runs the CLI on a single mounted repository, with the CLI's exit codes passed through, so it can stand in for `npx` in a job that has no Node.

```bash
mkdir -p atlas-data repos
cp docker/fleet.example.yml atlas-data/fleet.yml
docker compose -f docker/compose.example.yml up -d
```

`atlas-data` is the memory; deleting it is the only way to forget.

## What it reads

- **Doors.** Every workflow under `.github/workflows/`: triggers, the files its steps run and the files they only check (eslint, ruff, mypy, black, flake8, pylint, bandit, tsc) by the conventions of the tools they name, what it stages and pushes, here or in a clone of another repository it made in the step, what it dispatches, publishes (npm, PyPI, crates.io, RubyGems, a container image, the VS Code Marketplace, Open VSX, the Hugging Face Hub, a record on Zenodo), releases or deploys, and the issues or pull requests it opens. Every command the root or a workspace manifest installs (`bin` in `package.json`, `[project.scripts]` in `pyproject.toml`; `[[bin]]`, `src/main.rs` and `src/bin/*` in a `Cargo.toml` crate, a Tauri crate's bin as the desktop app people install, `run/main_scene` in `project.godot` as the game) and the entry of a published package, as doors of their own; the file each names is an entry point of its part. A tracked file handed to a tool with no rule is a checked run; a `cd` moves the rest of the step; `astro build`, `vite build` and `vite dev` run the site's config and `src/`; a job or step gated by an `if` on the event, the ref, its type or an input keeps its runs, sends and stages to that trigger. `pnpm` and `yarn` scripts resolve like `npm run`, workspace filters included; a run of a build output (`node dist/cli.js`) is a run of its source, placed through the entry a bundler's build names (esbuild `--outfile`/`--outdir` and its `build()` calls, tsup `-d`, rollup `-o`/`-d`, `vite build --ssr`), then through the tsconfig the build script names, and never through what is on disk; a helper that hands literal command text to a shell is followed one level; `docker build`, `python -m build` and `pyinstaller` run what they start (a Dockerfile's `ENTRYPOINT` or `CMD`, traced through stages, `WORKDIR` and `COPY`) and check what they pack; syntax checks (`node -c`, `py_compile`, `bash -n`) are checks; a job held off an event with `!=` keeps its sends to the events that remain; a push to a branch the job made, or to a branch kept for its own sake, is said as such and never as a commit into the repository; a package entry is a published door only when a door publishes it, and every `exports` subpath is named. A glob in a package script is expanded the way the job's shell expands it (`**` is one directory level under `sh`; unexpanded under cmd), and the files it leaves out are reported; a test runner's glob over built output (`node --test dist/**/*.test.js`) runs the sources it was built from; `node node_modules/<tool>/…` is that tool; among doors reaching as far, the pull request's wins whatever it runs, and the tie sentence names every tied door. A shell `for` over literal words is unrolled, so each package it publishes is named; a `git add` is neither a write nor a read, and what a step's own redirect or `tee` writes, following `cd`, is the door's; a package whose every exported file starts a program as it loads is its entry and no library; a private workspace member's bin is a command bundled into the package that names its built path. `cargo test` and `nextest` execute test targets and the files holding their own unit tests, `cargo run` and `bench` execute, `build`, `check`, `clippy`, `doc`, `fmt` and `install` are checks, with Cargo's package selection (`-p`, `--workspace`, `--exclude`, `--manifest-path`, `default-members`) honoured; `cargo tauri` and `tauri build`/`dev` run the crate after its `beforeBuildCommand`; the godot binary is recognised by its path, `--script` executes, GUT and gdUnit4 run tests, `gdlint` and `gdformat` check, and an export is a send ("exports the game for Linux"); a job that checks the repository out into its own `path:` is read from inside that directory.
- **Parts and imports.** JavaScript, TypeScript, TSX, Python, Rust and GDScript, parsed with tree-sitter; imports resolved with the rules the runtime uses, including workspace package exports without `node_modules`, tsconfig chains from tracked files only, Python source roots and declared dependencies, and dynamic imports with literal names. Resolution does not depend on what is installed. A drive-letter, absolute or `~` path is external on every host and never read from disk, so the same commit maps the same everywhere. Workspace members declared in `package.json` `workspaces` or `pnpm-workspace.yaml` resolve from the manifests with no `node_modules`; a bare name no manifest declares, a `workspace:` spec with no member, and a missing `file:` or `link:` spec are each counted unresolved with their reason, never dropped. When a file fails to parse it is parsed once more after a rewrite that keeps every byte offset (`typeof import(…)` and `import(…).T[]` become underscores with the specifier kept as an import; a bare `&` in JSX text becomes a space; a raw NUL byte becomes a space; `abstract` used as a name, a `<` with a space on each side on a failing line, and a decimal character reference past five digits are rewritten), kept only when the whole file then parses. Every file is read as git stores it: CRLF becomes LF in a text file unless the repository's own tracked `.gitattributes` says otherwise, so a checkout with `autocrlf` maps identically to one without. A client file's `/…` paths matched against a server file's routes are an edge of kind `http`. Rust imports follow the module tree as rustc builds it: `mod` resolves to `name.rs`, `name/mod.rs` or `#[path]`, `use` through `crate`, `self`, `super`, child modules, `path =` dependencies and the package's own lib; other declared crates and std are external, an undeclared crate is unresolved, and `include*!` macros are reads. GDScript resolves `res://` from the project root: `extends "…"` and `preload` are static imports, `load` with a literal or a const a dynamic one, a scene's `[ext_resource]` lines make scripts and scenes imports and other resources reads, and a `class_name` or an autoload is a global name. A crate is a part of its own and `init` proposes one per crate; a `project.godot` directory is a part.
- **Landing places and readers.** The tracked paths that code writes to and reads from, found in call expressions and followed through joins and helpers; raw GitHub URLs and quoted paths in files it does not parse, marked as found by text; shell scripts' and workflow steps' redirections and moves. A bare filename written through a variable root, or an open prefix, is recorded weak and never makes a place look generated. A written-out path that names a file lands on that file, not its directory, and the places a door writes inside one part are named by the deepest directory they share. A path built from the directory the command is run in (`process.cwd()`, a relative path resolved at run time, `dir || "."`) from the home directory or from a temporary directory (`tmpdir()`, `mkdtemp`, `tempfile.mkdtemp`, `gettempdir`) is counted outside; a write into a file the repository does not track is counted, never placed; a tracked file whose writers read it first has a block written by them, unless the read is only compared with what is about to be written; a write guarded against CI, behind a flag every run of a door passes, or behind a main guard the door never runs the file through, is not credited to that door; Python `Path` joins are followed. Markdown links and packaging lists are not readers; an import of a written module and an Astro site's content directories are. A path from a helper that returns a home or working directory, from an environment variable, or from an argument the caller passes is counted outside as well; an import of `package.json` or `pyproject.toml` is a read of that file, not an edge between parts; a test's reads are readers, marked as from tests; in Markdown only what its code spans and fences read counts, never a path in prose. A path built from `process.argv` or a CLI-arguments object is the caller's, values destructured from it included; a named inner function is read once per call with its parameters bound to what each call passes; a write guarded by `!existsSync`, an early return when the file exists, or the catch of a read is a bootstrap; a write under the working directory that spells a tracked place lands there, marked as from the working directory; in an argument list a path joined from a repository-root constant reads as that path; PowerShell `Copy-Item` and `Move-Item` are a read and a write, `Get-Content` a read, `Set-Content` and `Out-File` writes. A `for-of` over a literal array binds each element to its name and an object's properties to their destructured names; a reader of a written file's parent directory reads the file; an installed command's working-directory writes are the user's even when a workflow also runs the file. Rust `fs::write`, `create_dir*`, `copy`, `rename`, `File::create` and `OpenOptions` with write are writes, `read_to_string`, `read`, `read_dir` and `File::open` reads, followed through `Path`, `PathBuf`, `.join`, `let`, `const` and `CARGO_MANIFEST_DIR`; clap and argh fields are the caller's. GDScript `FileAccess.open` by mode, `ResourceSaver.save`, `DirAccess` and `save*` calls on `res://` paths land here; `user://` is the player's data directory, counted apart.
- **The order of work.** For the files a door runs and the files they call into, the cross-file calls of each entry function in order, with calls inside inline callbacks counted where they sit, same-file calls spliced in place, and constructed objects' method calls named with their class. A callback handed to a registrar (`server.tool(…)`, `.on(…)`) is not a step of the function that registers it, and an early return is said once as an alternative ("Or, when the query is empty, X does … instead.").
- **History.** Files that change together over the last 180 days. The shared-commit floor falls to 3 when fewer than 20 source files reach 10 revisions and rises back to 10 only at 25, starting from the floor the previous map used, so a repository near the line does not flip between maps; the window line states the rule and the confidence is stated on the page.

## What it cannot see

Paths built at run time are counted, not named. Imports that do not resolve are counted, and a declared dependency that shares a name with a local module is said to be the dependency. Commands whose arguments are built at run time are not followed, and the page says how many of them are in tests. A file the vendored grammar cannot parse is named, up to three, then counted by part with the construct that stopped it. Imports of paths outside the repository, writes to files it does not track, and writes to the directory the command is run in, the home directory, a temporary directory or a path the caller passes are counted and listed; a write whose path is a function parameter is settled from the calls that parameter is given, up to three hops, in JavaScript and TypeScript; in Python it is still counted among those built at run time. A claim that nothing writes, reads or imports is qualified by the count of files the parser could not read; the rewrite pass lets it read `typeof import(…)`, `import(…).T[]`, a bare `&` in JSX, a raw NUL byte, `abstract` as a name, a spaced `<` comparison and a long decimal character reference, but a construct spread over lines stays unread. A package script's glob is expanded as the job's shell would, and the test files that expansion leaves out of CI are listed. Links over HTTP between a client and a server in this repository are drawn as edges; GDScript writes and reads to `user://` are counted apart as the player's data directory; Rust method calls on values and calls inside macro arguments are not followed for the order of work; deploy files no workflow runs are named: an image a workflow builds and none pushes, a Hugging Face Space nobody uploads, a Docker MCP Catalog entry no workflow submits. Type-only imports count as imports.

## The map as a gate

This repository runs `atlas check` in its own CI and in `npm run verify`, and the pull-request comment on every change. The check found two things in its first days, a test that loaded a module through a computed dynamic import and a resolver that depended on whether a site's `node_modules` was installed, and both were fixed at the class, with fixtures that fail against the previous code.

The dogfood swarm reads the map too: `swarm init` drafts a run's domain map from the parts and refuses a draft that leaves a file in no domain or in two, every lane's brief carries its parts' "What breaks what" rows and `explain` for its entry points with the "cannot see" list beside them, `swarm verify` runs `atlas check` and records the structural delta of an amend wave, and `swarm advance` stops on a delta nobody asked for. A repository without a map swarms from the hand template exactly as before.
